I use AI coding agents daily, across research, implementation, debugging, test writing,
review, and documentation. They have measurably changed how much ground I cover in a day.

They have not changed who is accountable for the result, and the gap between those two facts
is where most of the bad outcomes live.

## What they are genuinely good at

**Exploring unfamiliar code.** Reading a large codebase to answer a specific question is
work agents do well and I find tedious. This is probably the highest-value use I have found.

**Mechanical implementation.** Once the design is decided, writing the obvious version of it
is fast and mostly correct.

**First-pass review.** Not judgment — pattern matching. Inconsistent error handling, a
missed null case, a caller that was not updated. Real findings, cheaply.

**Documentation and tests for code that already works.** Low risk, genuinely tedious, easy to
verify.

## What they are bad at, in ways that are easy to miss

**Knowing what not to build.** An agent asked to add a caching layer will add a caching
layer. It will not ask whether the endpoint is called twice a day. Every YAGNI decision is
still yours.

**Recognising the real root cause.** Given a symptom, an agent will produce a fix for the
symptom, and the fix will look correct. It will not usually grep every caller and notice
that four other paths have the same bug.

**Being wrong out loud.** The failure mode is not "I do not know". It is a fluent, plausible,
wrong answer — which is considerably more dangerous than an error.

<Callout title="The rule I actually follow">
  An agent can write code I could have written. It must not make a decision I could not
  defend. If I cannot explain why the code is shaped this way, it does not merge — regardless
  of whether it passes.
</Callout>

## How this fits into an engineering loop

The loop does not change. What changes is how much of each step is mechanical.

**Explore** — heavily agent-assisted. Reading, tracing, summarising.
**Design** — mine. This is the step where the expensive mistakes happen.
**Implement** — agent-assisted, reviewed as if it came from a competent stranger.
**Test** — agent-assisted, but I decide what is worth testing.
**Review** — agent first pass for the mechanical findings, then a human read for the ones
that need context.
**Ship** — mine.
**Learn** — mine, and the step people skip.

## The review discipline that matters

Treat agent output exactly as you would a pull request from a capable engineer who has no
context on your product.

That framing gets it right in both directions. You would not rewrite their work out of
suspicion, and you would not merge it without reading it. You would check the edge cases they
could not have known about.

The specific things I check every time: does this handle the failure path, does it match the
idioms already in this file, and did it change more than the task required.

## Why I do not call myself an AI engineer

I use AI as a tool for software engineering. That is different from engineering ML systems,
and conflating the two overstates one and undersells the other.

The value I offer a team is engineering judgment. Agents make me faster at executing that
judgment. They do not supply it, and any pitch that suggests otherwise should be treated with
suspicion.
