Every Flutter project eventually meets the same wall. A product manager asks for something
perfectly reasonable — detect a screenshot, change the app icon, read the system's usage
data — and there is no Dart API for it, because it is not a Flutter concept at all. It is an
operating system concept.

This is the most interesting part of mobile engineering, and it is where "write once, run
anywhere" stops being the useful frame.

## The framework boundary is not a bug

Flutter renders its own UI. That is why it is consistent across platforms, and it is also
precisely why it cannot expose platform capabilities it does not own.

Anything that touches the OS rather than the pixels — permissions, background execution,
system notifications, hardware, secure storage, device policy — sits outside the framework
by construction. Flutter's answer is the platform channel: you write the Kotlin, you write
the Swift, and you agree on a message format between them.

## The real problem is that the platforms disagree

The tempting mental model is that a platform channel is a bridge between one Dart function
and one native function. In practice the two native sides are rarely implementations of the
same idea.

Screenshot detection is the clearest example. On iOS, the system posts a notification after
a screenshot is taken, and you observe it. On Android there is no equivalent event; the
usual approach observes media content changes, which brings a permission story and a
different set of false positives.

Those are not two implementations of "detect a screenshot". They are two different
mechanisms whose outcomes overlap most of the time.

<Callout title="The design question">
  The question is never "how do I bridge this". It is "what is the honest common denominator,
  and what do I do about the part that does not fit".
</Callout>

## Three ways to handle divergence

**Expose the intersection.** Only surface what both platforms genuinely support. Simple,
predictable, and sometimes uselessly small.

**Expose the union, explicitly.** Provide the platform-specific capability with a name that
makes it obvious it is platform-specific. An `iosBadgeNumber` parameter is honest. A
`badgeNumber` parameter that silently no-ops on Android is a bug report waiting to happen.

**Fail loudly.** If a capability is unavailable, throw or return an explicit unsupported
result. Never a plausible-looking default — a `false` that means "not supported" is
indistinguishable from a `false` that means "no", and the caller will conflate them.

```dart
// Honest: the caller cannot mistake this for cross-platform behaviour.
if (Platform.isIOS) {
  await FlutterDynamicIconPlus.setApplicationIconBadgeNumber(3);
}
```

## Implement natively first, design the Dart API last

The mistake I made early was designing the Dart API first, then trying to make both platforms
satisfy it. That produces an API shaped by wishful thinking, and it discovers the platform
differences at the worst possible time — after the interface is public.

Now I do it in the other order. Get Android working idiomatically. Get iOS working
idiomatically. Only then look at both and ask what a caller should reasonably see.

The API gets narrower every time I do it this way. That has been a good sign.

## What this means for hiring and architecture

If your product needs the platform, you need engineers who understand the platform. Flutter
proficiency does not substitute for knowing how Android's lifecycle actually behaves, or what
iOS does to a background process.

Cross-platform is a delivery strategy. It is not, past a certain point, an engineering one.
