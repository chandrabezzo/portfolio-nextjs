I have built Flutter applications from scratch and inherited them mid-flight. The inherited
ones taught me more, because they show you which early decisions were load-bearing and which
were decoration.

This is what I now do at the start of a project, and — more usefully — what I deliberately
do not.

## Decide boundaries early, because they are the expensive part

Almost every structural decision is reversible. Module boundaries are the exception.

Renaming a class is a refactor. Splitting a feature that has grown tendrils into six other
features is a project. So boundaries are the one thing worth being deliberate about before
the code exists.

The boundary I care about most is not `data / domain / presentation`. It is the line between
*what the product does* and *what the platform happens to provide*. That line is where
requirements churn, and it is where a wrong boundary hurts most.

## What I decide on day one

**Module boundaries by feature, not by layer.** A feature owning its own data, logic, and UI
is easier to delete than a layer shared by fourteen features. Deletability is the property I
optimise for, because most code is eventually wrong.

**One state management approach, for the whole team.** Which one matters far less than that
there is exactly one. Two approaches in one codebase is not flexibility; it is two idioms
every reviewer has to hold in their head.

**Where platform code is allowed to live.** Native integration should be behind an interface
owned by the app, not scattered through feature code. When a plugin's API changes, you want
one file to update.

**How errors surface.** Decided once, early. Retrofitting a consistent error model across a
mature app is genuinely painful.

## What I deliberately defer

**Dependency injection sophistication.** Start with constructor parameters. Reach for a
service locator when the wiring actually hurts, not before.

**Abstraction over anything with one implementation.** An interface with a single
implementor is speculative. It has a cost today and a benefit that may never arrive.

**Premature modularisation into packages.** Directory boundaries hold the same discipline as
package boundaries at a fraction of the tooling cost. Promote to packages when there is a
real second consumer.

<Callout title="The recurring mistake">
  Almost every over-structured Flutter codebase I have inherited was built by a good engineer
  anticipating a requirement that never arrived. The structure was not wrong when it was
  written. It was just answering a question nobody asked.
</Callout>

## Performance is a structural property

Most Flutter performance problems I have diagnosed were not algorithmic. They were rebuild
scope: state placed too high in the tree, so a change that affects one widget repaints a
subtree.

That is a structural bug, not a performance bug, which is why profiling after the fact so
often points at a symptom. The fix is usually to move state down, not to memoise harder.

## The honest summary

Structure is a bet about what will change. Feature boundaries bet that features get added
and removed — which they reliably do. Elaborate layering bets that implementations get
swapped — which they rarely do.

Make the bet you can actually justify from the product you are building, not from the
architecture diagram you saw in a talk.
